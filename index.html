Selected work

Problems we were hired to solve

Agencies, restaurants, tour operators and cultural companies come to us with an operation that stopped scaling. These are the products we shipped for them.

Worker · marketing agency

Worker Brain

Multi-channel intelligence for an agency running 45 accounts.

The problem
Answering a client's "how are we doing?" meant opening five platforms: Meta Ads, Google Ads, email, ecommerce and leads. The data lived apart, and the real risk was handing the client a number that did not hold up.
What we built
A platform that syncs eight native integrations into one canonical daily snapshot, runs alerts per channel, and pushes three Slack digests (daily briefing, weekly review, monthly report) with what to look at first. An AI analyst answers on top of each client's already loaded data.
Result
45 accounts operate on a single surface. The team opens the panel when a digest flags something, and every number on screen comes from the same snapshot.
  • Next.js
  • TypeScript
  • Firestore
  • Claude
  • Gemini
  • Slack
  • Vercel
Worker · product for restaurants

Comanda Directa

One codebase serving the QR menu of every restaurant on the platform.

The problem
The ordering system had been built for a single venue. Adding the second one meant a new database project and a new deployment per client, so the product could not grow past a handful of restaurants.
What we built
A multi-tenant engine: one Next.js app serves the landing page and the menu of every client, against a single Supabase project. Each venue loads its menu from its own panel or imports the spreadsheet it already had, sets service modes, payment methods and delivery zones, and receives orders already written out on WhatsApp. A Chrome extension prints the ticket on the counter printer.
Result
Onboarding a new restaurant is one database row, one menu load and one QR code. Every product improvement reaches all venues at the same time.
  • Next.js
  • Supabase
  • Multi-tenant
  • Chrome extension
  • WhatsApp
Lati Travel · tour operator

latitravel.com

A WordPress catalogue rebuilt as 251 static pages.

The problem
The redesign on the table was a single-page app: search engines could not see a single price. The mockup also promised things the business did not have, from review ratings to free cancellation and instant confirmation.
What we built
A static Astro site with real HTML on every URL: 158 bookable experiences imported from the live catalogue, 24 destination pages and 42 guides. The 258 indexed WordPress URLs redirect with 301s verified against the deployment, and 314 tests fail the build if an unbacked promise comes back.
Result
Live since 24 August 2026, with every experience, destination and guide as its own indexable URL, and nothing on the page the operation cannot honour.
  • Astro
  • SEO and GEO
  • GitHub Actions
  • Vercel
Presencia · restaurant

Digital menu and floor panel

The problem
Five separate menus on paper (dinner à la carte, lunch, wine, cocktails and the café next door), with prices that move and dishes that run out mid-service.
What we built
A mobile-only QR menu reading live from Firestore, plus a password-protected panel. Wine keeps its own numbering, so adding a dish never shifts "number 47".
Result
Marking a dish as sold out reaches the phones already open, with no reload. Bookings moved from a spreadsheet to their own screen.
  • Next.js
  • Firestore
  • Playwright

Worker · engineering

Security and quality gates for AI-written code

The problem
Writing code with AI at speed leaks secrets into commits and lets quality drift down one pull request at a time.
What we built
A config-driven enforcement layer: each project declares its stack in one manifest and the same hooks run for Java, Python or TypeScript. Secret scanning, a blocking pre-push gate, static analysis and dependency audit.
Result
One framework covers every repository. Quality ratchets let the metrics go down and never up, and adoption is additive: a key missing from the manifest is a silent skip, not a broken build.
  • Config-driven
  • Security gates
  • Any language

Alynk · portfolio reporting

Portfolio statements on the phone

The problem
The daily portfolio statement was a spreadsheet emailed to each account holder.
What we built
A private panel behind a login that reads the same file the existing script generates. It recalculates nothing: the spreadsheet stays the source of truth, and a validation step re-runs the reconciliation checks on the extracted data.
Result
The account holder opens the statement on their phone, and a parsing error stops the pipeline instead of reaching the screen.
  • Python
  • TypeScript
  • Reconciliation checks
GymCounter · training app

Training plans and logging with no connection

The problem
A gym routine gets dropped for two reasons: the plan does not move on with the person, and logging a set fails exactly where there is no signal.
What we built
A progressive web app with a protocol engine: each goal builds its own cycle of days, with warm-up and deload weeks across a 180-day program. Logging runs against IndexedDB and a service worker, so it works offline and syncs later. Subscriptions run on Stripe, with checkout, a self-service portal and idempotent webhooks.
Result
Training and logging work in the basement of the gym, and subscribing or cancelling never goes through support.
  • Next.js
  • React 19
  • Firebase
  • Stripe
  • Offline PWA
